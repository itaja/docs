**Webhooks** let Itaja push real-time HTTP notifications to your server the moment something meaningful happens — a payment settles, a charge fails, a subscription is cancelled. Rather than polling the API for status changes, you register an HTTPS endpoint and Itaja delivers a signed JSON payload to it for every event you subscribe to. This makes it easy to trigger downstream actions in your application: unlocking access, sending receipts, alerting your team, or updating your database — all without delay.

---

## Webhook events

Itaja emits the following event types. You can subscribe to any combination when registering a webhook endpoint.

| Event | Triggered When |
|---|---|
| `payment.succeeded` | A payment is settled successfully |
| `payment.failed` | A payment attempt fails |
| `payment.processing` | The customer confirms the charge; awaiting provider settlement |
| `subscription.created` | A new subscription is created |
| `subscription.cancelled` | A subscription is cancelled |
| `subscription.past_due` | A subscription enters the `past_due` state after a failed payment |
| `subscription.paused` | A subscription is paused |
| `subscription.resumed` | A paused subscription is resumed |
| `customer.created` | A new customer record is created |

## Create a webhook

`POST /webhooks`

Registers a new webhook endpoint. Itaja immediately begins delivering matching events to the URL you provide.

### Body parameters

<ParamField body="url" type="string" required>
  The HTTPS URL of your endpoint. Itaja sends a `POST` request to this URL each time a subscribed event fires (e.g., `"https://yourapp.com/webhooks/itaja"`).
</ParamField>

<ParamField body="events" type="array" required>
  An array of event type strings to subscribe to (e.g., `["payment.succeeded", "payment.failed"]`). See the [Webhook events](#webhook-events) table above for all available values.
</ParamField>

### Via the dashboard

Go to **Settings → Webhooks → Add Endpoint**, enter your HTTPS URL, and select the events you want to receive.

### Request example

```bash
curl -X POST https://api.getitaja.com/v1/webhooks \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://yourapp.com/webhooks/itaja", "events": ["payment.succeeded", "payment.failed", "subscription.cancelled"]}'
```

### Response `201 Created`

```json
{
  "data": {
    "id": "wh_mno345",
    "url": "https://yourapp.com/webhooks/itaja",
    "events": ["payment.succeeded", "payment.failed", "subscription.cancelled"],
    "active": true,
    "created_at": "2024-01-15T10:00:00Z"
  }
}
```

<ResponseField name="data.id" type="string">
  Unique identifier for the webhook endpoint. Use this ID to retrieve, update, or delete the endpoint.
</ResponseField>

<ResponseField name="data.url" type="string">
  The HTTPS URL Itaja delivers events to.
</ResponseField>

<ResponseField name="data.events" type="array">
  The list of event types this endpoint is subscribed to.
</ResponseField>

<ResponseField name="data.active" type="boolean">
  `true` when the endpoint is live and receiving events.
</ResponseField>

<ResponseField name="data.created_at" type="string">
  ISO 8601 timestamp of when the webhook endpoint was registered.
</ResponseField>

## List all webhooks

`GET /webhooks`

Returns a list of all webhook endpoints registered for your account.

### Request example

```bash
curl https://api.getitaja.com/v1/webhooks \
  -H "Authorization: Bearer YOUR_API_KEY"
```

### Response `200 OK`

```json
{
  "data": [
    {
      "id": "wh_mno345",
      "url": "https://yourapp.com/webhooks/itaja",
      "events": ["payment.succeeded", "payment.failed", "subscription.cancelled"],
      "active": true,
      "created_at": "2024-01-15T10:00:00Z"
    }
  ],
  "meta": { "total": 1 }
}
```

## Update a webhook

`PATCH /webhooks/:id`

Updates the endpoint URL or the list of subscribed events. Only the fields you provide are changed.

### Body parameters

<ParamField body="url" type="string">
  New HTTPS URL for the endpoint.
</ParamField>

<ParamField body="events" type="array">
  Replacement list of event type strings. This fully replaces the existing list — include all events you want to receive, not just the new ones.
</ParamField>

### Request example

```bash
curl -X PATCH https://api.getitaja.com/v1/webhooks/wh_mno345 \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"events": ["payment.succeeded", "payment.failed", "subscription.cancelled", "subscription.past_due"]}'
```

### Response `200 OK`

```json
{
  "data": {
    "id": "wh_mno345",
    "url": "https://yourapp.com/webhooks/itaja",
    "events": ["payment.succeeded", "payment.failed", "subscription.cancelled", "subscription.past_due"],
    "active": true,
    "created_at": "2024-01-15T10:00:00Z"
  }
}
```

## Delete a webhook

`DELETE /webhooks/:id`

Permanently removes the webhook endpoint. Itaja stops delivering events to the URL immediately.

### Request example

```bash
curl -X DELETE https://api.getitaja.com/v1/webhooks/wh_mno345 \
  -H "Authorization: Bearer YOUR_API_KEY"
```

### Response `200 OK`

```json
{
  "data": {
    "id": "wh_mno345",
    "deleted": true
  }
}
```

## Webhook payload

Every event Itaja delivers follows the same envelope structure: a top-level `id`, `type`, and `created_at`, plus a `data` object containing the relevant resource.

Below is an example payload for a `payment.succeeded` event:

```json
{
  "id": "evt_jkl012",
  "type": "payment.succeeded",
  "created_at": "2024-02-01T08:05:00Z",
  "data": {
    "id": "pay_ghi789",
    "subscription_id": "sub_def456",
    "customer_id": "cust_xyz789",
    "amount": 15000,
    "currency": "XOF",
    "status": "succeeded"
  }
}
```

<ResponseField name="id" type="string">
  Unique identifier for the event delivery. Use this to deduplicate events if your endpoint receives the same delivery more than once.
</ResponseField>

<ResponseField name="type" type="string">
  The event type (e.g., `payment.succeeded`). Use this field to route the payload to the correct handler in your application.
</ResponseField>

<ResponseField name="created_at" type="string">
  ISO 8601 timestamp of when the event was generated.
</ResponseField>

<ResponseField name="data" type="object">
  The resource associated with the event. The shape mirrors the corresponding API response object (payment, subscription, or customer).
</ResponseField>

## Signature verification

Itaja signs every webhook delivery with a secret key unique to your endpoint. You can find this secret in **Settings → Webhooks** after creating your endpoint. To verify a delivery, compute `HMAC-SHA256` of the raw request body using your webhook secret and compare the result to the value in the `X-Itaja-Signature` request header.

<Warning>
  Always verify the webhook signature before processing the event. Never trust webhook payloads that fail signature validation.
</Warning>

Here is a Node.js example:

```js
const crypto = require('crypto');

function verifyWebhook(rawBody, signature, secret) {
  const expected = crypto
    .createHmac('sha256', secret)
    .update(rawBody)
    .digest('hex');
  return crypto.timingSafeEqual(
    Buffer.from(signature),
    Buffer.from(expected)
  );
}
```

<Note>
  Use `crypto.timingSafeEqual` (or the equivalent in your language) rather than a plain string comparison. This prevents timing attacks that could allow an attacker to forge a valid signature.
</Note>

Pass the **raw request body bytes** — not a parsed JSON object — to the HMAC function. Parsing and re-serialising the body may alter whitespace or key order and cause verification to fail.

## Retries and delivery

If your endpoint returns any HTTP status other than `2xx`, or if no response is received within **10 seconds**, Itaja marks the delivery as failed and schedules a retry. Itaja retries failed deliveries up to **5 times** using exponential backoff:

| Attempt | Delay |
|---|---|
| 1st retry | 5 minutes |
| 2nd retry | 30 minutes |
| 3rd retry | 2 hours |
| 4th retry | 6 hours |
| 5th retry | 24 hours |

<Tip>
  Respond with HTTP `200` as quickly as possible — ideally before doing any heavy processing. Enqueue the payload and handle it asynchronously so you don't risk a timeout causing unnecessary retries.
</Tip>
